# Certified Chain

Certified Chain is a Next.js application for issuing, storing, and verifying blockchain-backed certificates. Institutions issue credentials through a wallet-connected workflow, certificate records are persisted in Neon Postgres, and verification reads both application state and Cardano anchoring data.

## Production Trust Model

- Certificate records live in Neon Postgres.
- Public verification queries certificate status by certificate number or unique identifier.
- Cardano anchoring stores a certificate hash and identifier reference, not the raw certificate payload.
- Certificate NFTs use Cardano 721 metadata with an IPFS-hosted SVG certificate image.
- Institutions can revoke certificates in the application database and, when the Aiken contract is configured, on-chain as well.
- Issuance now uses a durable `issuance_jobs` table so retries reconcile against a reserved server-side job instead of creating duplicate certificate rows.
- Midnight zero-knowledge proof support is present in the repo but should be treated as experimental until fully deployed and operated.

## Stack

- Next.js 16 App Router
- TypeScript
- Tailwind CSS and shadcn/ui
- Neon Postgres for application tables, users, and sessions
- Cardano via Mesh SDK and Blockfrost
- Pinata/IPFS for NFT certificate image storage
- Optional Aiken contract for trustless registry/revocation
- Optional Midnight integration for privacy-preserving proofs

## Main Product Flows

### Institution issuance

1. Institution admin signs in.
2. The app creates a server-side issuance job in `/api/issuance`.
3. The app renders the certificate NFT image and pins it to IPFS.
4. The client submits the Cardano transaction from the connected wallet.
5. The Cardano transaction mints the certificate NFT with 721 metadata.
6. The transaction result is reconciled through `/api/issuance/[jobId]`.
7. The certificate row is persisted exactly once and linked back to the issuance job.

### Certificate NFTs

Certificate NFT images are generated by `/api/certificates/[uniqueId]/nft-image`.

The generated SVG contains:

- institution name
- optional organization logo
- recipient name and email
- recipient position
- credential type
- issue and expiry dates
- certificate number and unique identifier
- certificate hash and transaction reference
- QR code that opens the certificate image route

The NFT metadata is available at `/api/certificates/[uniqueId]/nft-metadata`.

For wallet display, the app pins the SVG image to IPFS through `/api/certificates/[uniqueId]/pin-nft-image` and stores the NFT `image` field as an `ipfs://...` URL.

### Organization logos

Institution admins can add or change their logo from `/institution/dashboard`.

Logo behavior:

- The logo file is uploaded to Pinata/IPFS.
- The organization row stores the logo as `organization_image_name`, usually `ipfs://CID`.
- New certificate NFT images use the uploaded logo.
- If no logo is configured, the default LiteCert seal is used.
- The NFT image route embeds IPFS logos as image data inside the SVG so wallets and browsers are less likely to block the logo.

### Sharing certificates to recipients

Institutions can share a certificate in two ways:

- Send the public certificate view link: `/certificate/view?uniqueId=...`
- Transfer the certificate NFT from the institution wallet to the recipient wallet.

From `/institution/dashboard`, use the certificate row action menu and select `Transfer NFT`.

Transfer behavior:

1. Connect the institution wallet that currently holds the official certificate NFT.
2. Enter the recipient Cardano wallet address.
3. Sign the transaction.
4. The official NFT is sent to the recipient wallet.
5. If the institution wallet does not already have one, the same transaction mints an issuer copy back to the institution wallet.

Issuer-copy behavior:

- Official recipient asset: `WAL_JK_13`
- Institution archive asset: `WAL_JK_13_ISSUER_COPY`
- The issuer copy metadata includes `copyType: issuer_copy`.
- The issuer copy is a separate NFT, not a duplicate quantity of the official recipient NFT.
- If the issuer copy already exists in the institution wallet, the app does not mint another one.

This keeps the recipient’s official certificate NFT 1-of-1 while the institution keeps an archive/proof copy.

### Verification

1. Verifier looks up a certificate by `certificateNumber` or `uniqueIdentifier`.
2. The app loads the certificate record from Neon Postgres.
3. The UI checks Cardano metadata and, if configured, the contract UTxO state.
4. Status is rendered as `valid`, `revoked`, or `expired`.

### Revocation

1. Institution admin opens the dashboard.
2. The app optionally submits an on-chain revocation if the contract path is active.
3. The certificate row is updated to `revoked`.

## Environment

Use [.env.example](/home/mwihotidan/work/startups/certified-chain/.env.example) as the source of required variables.

Important:

- `NEXT_PUBLIC_*` values are browser-visible.
- Keep Pinata secrets server-side only.
- Configure Pinata with either `PINATA_JWT` or `PINATA_API_KEY` and `PINATA_SECRET_API_KEY`.
- Use a dedicated Blockfrost project per environment.
- Do not point development builds at production Supabase, Neon, or Cardano infrastructure.

## Database and RLS

Neon SQL migrations now live under [neon/migrations](/home/mwihotidan/work/startups/certified-chain/neon/migrations).

The older Supabase migration remains in [supabase/migrations](/home/mwihotidan/work/startups/certified-chain/supabase/migrations/20260526_production_hardening.sql) for reference, but it uses Supabase-specific RLS helpers and should not be applied directly to Neon.

The Neon schema introduces:

- `organizations`
- `app_users`
- `app_auth_sessions`
- `certificates`
- `issuance_jobs`
- `audit_logs`
- App-enforced institution scoping in the Next.js API routes

Before deploying, make sure institution users in `app_users` include:

- `role`
- `institution_id` for institution admins

## Local Development

```bash
bun install
bun run dev
```

Run tests with:

```bash
bun run test
```

Run production checks with:

```bash
./node_modules/.bin/tsc --noEmit
bun run build
```
